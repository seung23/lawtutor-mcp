# LawTutor - 이렇게 동작합니다

> 바이브코딩으로 만들었지만, 내가 만든 것이 어떻게 돌아가는지는 알아야 하니까.

---

## 한 줄 요약

**사용자가 Claude.ai에 법학 질문 → Claude가 이 PC의 법령 DB를 검색 → 검색 결과로 답변 생성**

## 핵심 개념 3가지

### 1. MCP (Model Context Protocol)

Claude에게 **외부 도구를 붙여주는 규격**이다.

- Claude는 똑똑하지만, 최신 한국 법령 데이터를 갖고 있지는 않다.
- MCP를 통해 "법령 검색 도구"를 Claude에 연결하면, Claude가 필요할 때 알아서 도구를 호출한다.
- 이 서버는 **6개 도구**를 제공한다:

| 도구 | 하는 일 | 예시 질문 |
|------|---------|----------|
| `search_law` | 법령 조문 검색 | "처분의 사전통지란?" |
| `search_precedent` | 대법원 판례 검색 | "처분성이 인정된 판례는?" |
| `search_constitutional_decision` | 헌재 결정례 검색 | "기본권 침해 판단 기준은?" |
| `search_legal_interpretation` | 법제처 해석례 검색 | "이 조문의 실무 적용은?" |
| `fetch_article_by_number` | 조문번호로 직접 조회 | "행정절차법 제21조 알려줘" |
| `fetch_case_by_number` | 사건번호로 직접 조회 | "2018두12345 판결 알려줘" |

### 2. 벡터 검색 (RAG)

"행정절차법 제21조"처럼 정확한 번호를 아는 경우는 단순 조회로 충분하다.
하지만 "처분의 사전통지 요건이 뭐야?" 같은 자연어 질문은 **의미를 이해하는 검색**이 필요하다.

```
"처분의 사전통지 요건이 뭐야?"
        │
        ▼
  ┌──────────────┐
  │  BGE-M3 모델  │  ← 이 PC의 CPU에서 돌아감 (여기서 1~3초 걸림)
  │  (임베딩 모델) │
  └──────┬───────┘
         │ [0.12, -0.34, 0.56, ...] (1024개의 숫자 = 질문의 "의미")
         ▼
  ┌──────────────┐
  │   Qdrant DB   │  ← 미리 저장된 모든 법령 조문도 같은 방식으로 벡터화돼 있음
  │  (벡터 검색)   │
  └──────┬───────┘
         │ 의미가 가장 비슷한 조문 상위 5개 반환
         ▼
  행정절차법 제21조 (처분의 사전통지) ← 이게 가장 관련도 높음!
  행정절차법 제22조 (의견청취)
  ...
```

**왜 BGE-M3인가?** 한국어를 잘 이해하는 임베딩 모델이고, 무료이고, 로컬에서 돌릴 수 있다.

### 3. Cloudflare Tunnel

이 PC를 인터넷에 안전하게 노출하는 방법이다.

```
일반적인 방법 (위험):
  인터넷 → 공유기 포트포워딩 → 이 PC
  (해커가 직접 PC에 접근 가능, DDoS 공격에 무방비)

Cloudflare Tunnel (우리 방식):
  인터넷 → Cloudflare 서버 → 암호화된 터널 → 이 PC
  (Cloudflare가 방패 역할, PC의 IP 주소 노출 안 됨)
```

- `lawtutor.dev` 도메인으로 접속하면 Cloudflare를 거쳐서 이 PC에 도달한다.
- HTTPS, DDoS 보호, 악성 트래픽 차단 모두 Cloudflare가 처리한다.
- 이 PC에서는 `cloudflared`라는 프로그램이 터널을 유지한다.

## 데이터는 어디서 왔나?

모든 데이터는 **국가법령정보센터 OPEN API** (`open.law.go.kr`)에서 수집했다.

```
국가법령정보센터 API
        │
        │ XML 응답
        ▼
┌───────────────┐     ┌──────────────┐     ┌──────────────┐     ┌─────────┐
│  1. 수집       │────▶│  2. 파싱      │────▶│  3. 청킹      │────▶│ 4. 저장  │
│  (collectors/) │     │  (parsers/)  │     │  (chunking/) │     │ (Qdrant)│
│                │     │              │     │              │     │         │
│ API 호출 →     │     │ XML → JSON   │     │ 긴 조문을     │     │ 벡터로   │
│ XML 저장       │     │ 구조화       │     │ 적절한 크기로  │     │ 변환해서 │
│ (data/raw/)    │     │ (data/parsed/)│    │ 자름          │     │ DB에 저장│
└───────────────┘     └──────────────┘     └──────────────┘     └─────────┘
```

수집 대상:
- **법령**: 행정절차법, 행정소송법, 행정심판법 등 10개 법률 + 시행령/시행규칙
- **판례**: 행정법 관련 대법원 판례
- **헌재결정례**: 기본권, 위헌심사 관련 결정
- **법령해석례**: 법제처의 유권해석

## 폴더 구조 요약

```
law_agent/
├── src/lawtutor/           ← 메인 코드
│   ├── collectors/         ← 1단계: API에서 데이터 수집
│   ├── parsers/            ← 2단계: XML을 JSON으로 파싱
│   ├── chunking/           ← 3단계: 문서를 검색 단위로 자름
│   ├── embeddings/         ← BGE-M3 임베딩 모델 래퍼
│   ├── vector_store/       ← Qdrant DB 연결/관리
│   ├── retrieval/          ← 검색 로직 (벡터 검색 + 직접 조회)
│   ├── mcp_server/         ← MCP 서버 (도구 정의 + HTTP 앱)
│   ├── models/             ← 데이터 모델 (Pydantic)
│   ├── evaluation/         ← 검색 품질 평가 도구
│   ├── config.py           ← 환경변수 설정
│   └── constants.py        ← 상수 정의
│
├── data/
│   ├── raw/                ← API 원본 응답 (XML)
│   ├── parsed/             ← 파싱된 데이터 (JSON)
│   └── eval/               ← 평가 데이터셋
│
├── scripts/                ← 실행 스크립트
│   ├── run_server.py       ← 로컬 개발 서버 실행
│   └── run_eval.py         ← 검색 품질 평가 실행
│
├── qdrant_storage/         ← Qdrant 벡터 DB 데이터 (Docker 볼륨)
├── bge_m3_cache/           ← BGE-M3 모델 캐시 (Docker 볼륨)
│
├── docker-compose.yml      ← Docker 컨테이너 3개 정의
├── Dockerfile              ← 앱 서버 빌드 설정
└── .env                    ← 비밀 설정 (API 키, 토큰)
```

## Docker 컨테이너 3총사

```
docker compose up -d  ← 이 한 줄로 3개가 동시에 뜬다

┌─────────────────────────────────────────────┐
│              Docker Desktop                  │
│                                             │
│  ┌─────────────┐  ┌────────────────────┐    │
│  │   qdrant     │  │      app           │    │
│  │  (벡터 DB)   │◀─│  (LawTutor 서버)    │    │
│  │              │  │                    │    │
│  │ 법령/판례    │  │ FastAPI + BGE-M3   │    │
│  │ 벡터 저장    │  │ MCP 도구 6개       │    │
│  └─────────────┘  └────────────────────┘    │
│                            ▲                │
│  ┌─────────────┐           │                │
│  │ cloudflared  │───────────┘                │
│  │ (터널 연결)   │  lawtutor.dev ↔ app:8000  │
│  └─────────────┘                            │
└─────────────────────────────────────────────┘
```

- **qdrant**: 법령 데이터가 벡터로 저장된 데이터베이스
- **app**: 검색 요청을 받아 처리하는 서버 (BGE-M3 모델도 여기서 동작)
- **cloudflared**: 이 PC와 Cloudflare 사이의 터널을 유지

## 왜 느릴 수 있나?

| 상황 | 원인 | 소요 시간 |
|------|------|----------|
| 컨테이너 첫 시작 | BGE-M3 모델 로딩 (~2.5GB) | 30초~2분 |
| `search_*` 도구 호출 | CPU에서 임베딩 벡터 계산 | 1~3초 |
| `fetch_*` 도구 호출 | 벡터 계산 없이 직접 조회 | <1초 |
| Cloudflare 경유 | 네트워크 왕복 | ~0.1초 |

**첫 번째 요청이 특히 느린 이유**: 모델이 "게으른 로딩(lazy loading)"으로 설계돼 있어서, 서버가 시작된 후 첫 검색 요청이 올 때 비로소 BGE-M3를 메모리에 올린다.

## 운영 체크리스트

서비스가 정상 동작하려면:

- [ ] 이 PC가 켜져 있어야 한다 (절전모드 X)
- [ ] Docker Desktop이 실행 중이어야 한다 (자동 시작 설정 권장)
- [ ] 인터넷이 연결돼 있어야 한다
- [ ] `docker compose ps`로 3개 컨테이너가 모두 Up인지 확인

문제가 생기면:
```bash
# 상태 확인
docker compose ps

# 로그 확인
docker compose logs app --tail=20

# 전체 재시작
docker compose restart

# 완전히 새로 시작
docker compose down && docker compose up -d
```
